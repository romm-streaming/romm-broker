You don't run the broker by itself. It ships inside
[linuxserver/docker-webstation](https://github.com/linuxserver/docker-webstation),
on the `romm` branch, as the image `lscr.io/linuxserver/webstation:romm`. That
image is a full Linux desktop, streamed to your browser with software called
selkies, with every supported emulator already installed and nginx (a web
server) in front. The broker is registered as one of the container's
background services, managed by an init system called s6, and it starts once
selkies's control plane (the part of selkies it talks to) is ready.

Setting this up for the first time? The [Quickstart](/docs/quickstart) walks
through this page in order, alongside the rest of the setup.

<Callout type="warn">
The image only works in Wayland mode (the graphics system newer Linux desktops
use) and is meant to run with a GPU. Without a GPU, the desktop itself still
works using software rendering, but most emulators will not.
</Callout>

## docker-compose

```yaml
---
services:
  webstation:
    image: lscr.io/linuxserver/webstation:romm
    container_name: webstation
    environment:
      - PUID=1000
      - PGID=1000
      - TZ=Etc/UTC
      - SUBFOLDER=/streaming/
      - BROKER_SECRET=change-me
    volumes:
      - /path/to/config:/config
      - /path/to/roms:/romm
      # optional: pre-seed RetroArch BIOS/firmware instead of drag-and-drop
      # - /path/to/bios:/config/.config/retroarch/system
    ports:
      - 3000:3000
      - 3001:3001
    shm_size: "1gb"
    restart: unless-stopped
```

## docker cli

```bash
docker run -d \
  --name=webstation \
  -e PUID=1000 \
  -e PGID=1000 \
  -e TZ=Etc/UTC \
  -e SUBFOLDER=/streaming/ \
  -e BROKER_SECRET=change-me \
  -p 3000:3000 \
  -p 3001:3001 \
  -v /path/to/config:/config \
  -v /path/to/roms:/romm \
  -v /path/to/bios:/config/.config/retroarch/system \
  --shm-size="1gb" \
  --restart unless-stopped \
  lscr.io/linuxserver/webstation:romm
```

The BIOS mount is optional. It only applies to RetroArch's shared system
directory, where RetroArch looks for BIOS and firmware files. Skip it (and
remove the commented-out line in the compose example above) if you'd rather
upload those files through the desktop instead. See
[Getting files into the container](/docs/emulators/setup#getting-files-into-the-container)
for the matching path to mount for other emulators.

## Parameters

| Parameter | Function |
| --- | --- |
| `-p 3000` | Plain, unencrypted web traffic (HTTP). This port must sit behind a reverse proxy. See [Reverse proxy](/docs/deployment/reverse-proxy). |
| `-p 3001` | HTTPS (encrypted), using a self-signed certificate, for connecting directly to the container while testing. |
| `-v /config` | The user's home directory inside the container. Holds emulator settings, BIOS and firmware, and save data. It's also where the broker keeps its pid record (a small file it uses to find the running emulator again after a restart) and its export directory. |
| `-v /romm` | Your ROM library, which you can mount read-only if you like. Activate (the call that launches a game) rejects any ROM path outside `ROM_ROOT` (default `/romm`), so RomM's `library_path` for this container must point here. |
| `-v .../retroarch/system` (optional) | A host folder already filled with BIOS and firmware, mounted at RetroArch's shared system directory (`RETROARCH_SYSTEM_DIR`, default `/config/.config/retroarch/system`) so you don't have to drag files into the desktop by hand afterward. See [Getting files into the container](/docs/emulators/setup#getting-files-into-the-container). |
| `--shm-size=1gb` | Sets the container's shared memory size. Recommended for all desktop images like this one. |
| `-e PUID` / `-e PGID` | The user ID and group ID (uid/gid) that the desktop, the emulators, and the broker all run as. Match them to the owner of your mounted directories so file permissions line up. |
| `-e SUBFOLDER` | The URL path the whole app is served under, default `/streaming/`. Must exactly match the path your reverse proxy mounts the container at, trailing slash included. |
| `-e BROKER_SECRET` | A shared password that RomM sends as the `X-Broker-Secret` header on the lifecycle endpoints (the API calls that start and stop sessions), so the broker knows the request really came from RomM. Unset, the broker refuses to start unless `BROKER_DEV_MODE` is also set, in which case it starts with those endpoints unauthenticated. |
| `-e BROKER_DEV_MODE` | Set to `true` to run the broker from source code mounted at `/broker`. See [Dev mode](/docs/container/dev-mode). |

Every other broker and emulator variable is optional. They're listed under
[Configuration](/docs/configuration).

### GPU

Mount your GPU into the container and the base image sets it up automatically,
for both rendering the desktop and encoding the video stream. No extra
variables are needed. The full guide, covering multi-GPU pinning (choosing
which GPU to use when you have more than one), hardware encoders, and
troubleshooting, is the selkies
[GPU acceleration page](https://docs.linuxserver.io/selkies/user-guide/gpu/#automatic-configuration).
Here's the minimum you need to add to the examples above:

<Tabs items={['Intel / AMD', 'NVIDIA']}>
<Tab value="Intel / AMD">

Open-source drivers only need the render node (a device file for the GPU)
passed through.

```yaml title="docker-compose"
    devices:
      - /dev/dri:/dev/dri
```

```bash title="docker cli"
  --device /dev/dri \
```

If your host has more than one GPU, pin (select) the node the container
should use:

```yaml
    environment:
      - DRINODE=/dev/dri/renderD129
      - DRI_NODE=/dev/dri/renderD129
```

</Tab>
<Tab value="NVIDIA">

Needs the NVIDIA container runtime installed on the host, with driver
version 595.80 or newer.

```yaml title="docker-compose"
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [compute,video,graphics,utility]
    devices:
      - /dev/nvidia-modeset:/dev/nvidia-modeset
```

```bash title="docker cli"
  --runtime nvidia \
  --gpus all \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,video,graphics,utility \
  --device /dev/nvidia-modeset \
```

`/dev/nvidia-modeset` is the device file that's easy to miss. The NVIDIA
container toolkit automatically adds `nvidia0`, `nvidiactl` and `uvm`, but not
the modeset device. Without it, the GPU can still detect itself, compute and
encode video, but the graphics system (Vulkan) can't actually display
anything on screen: emulators run without ever reaching the screen, and the
browser shows a black canvas. If the node does not exist on the host,
`nvidia-modprobe --modeset` creates it.

`--gpus all` on its own only turns on `compute,utility` for
`NVIDIA_DRIVER_CAPABILITIES`. That's why the cli example above sets `graphics`
explicitly, to match the `capabilities` list in the compose example.

<Callout type="warn" title="Unprivileged LXC needs more than this">
Proxmox LXC (Proxmox's own lightweight containers, different from Docker) is
not a tested or certified way to run selkies-based images like this one. The
supported way to run this on Proxmox is a dedicated VM running Docker. One
setup that's been confirmed to work (RTX 4060, driver 595.80, Open Kernel
Module) needed everything below, on top of the device mapping above:

- Run `chmod 666 /dev/dri/* /dev/nvidia-modeset` from a `/custom-cont-init.d`
  script (a script the image runs automatically at startup). The LXC passes
  these device files through at permission `0660`, and the host resets that
  on every reboot, so the container's `abc` user can't open them otherwise.
- Bind-mount (share directly from the host) what the toolkit skips:
  `/usr/lib/x86_64-linux-gnu/gbm/`, `/usr/share/egl/egl_external_platform.d/`,
  `libnvidia-egl-gbm.so.1*` and `/usr/share/glvnd/egl_vendor.d/10_nvidia.json`.
  Without these, the desktop falls back to software rendering (called Pixman)
  instead of using the GPU.
- `PIXELFLUX_WAYLAND=true`.

See [Issue #32](https://github.com/romm-streaming/romm-broker/issues/32) for
the full explanation.
</Callout>

</Tab>
</Tabs>

Some emulators (`DOLPHIN_VIDEO_BACKEND`, `XEMU_RENDERER`) are pinned to a
renderer known to work on the integrated AMD graphics this image is tested
on. Change these if your driver prefers Vulkan instead. PCSX2 has no such
pin: its renderer setting lives in `PCSX2.ini`, picked by its own setup
wizard. So a "Failed to initialize GS" startup error on an AMD integrated
GPU means RADV (AMD's Vulkan driver) failed to start on that hardware.
Switch PCSX2's renderer to OpenGL instead, in **Settings > Graphics**: it
uses a different driver (radeonsi) that's confirmed to work.

## First run

The container boots straight to the webstation desktop. Before you launch
games through RomM, every emulator you plan to use needs its BIOS, firmware,
or decryption keys set up, plus a quick controller check. Launch a `desktop`
session from RomM (or open `https://yourhost:3001/streaming/` directly) and
follow [Emulator setup](/docs/emulators/setup).

## Wiring it into RomM

RomM talks to the container over REST (a common way for apps to communicate
over plain HTTP) and embeds its room in an iframe (a webpage shown inside
another webpage). Add this to RomM's `config.yml`:

```yaml
streaming:
  containers:
    - platform: ps2
      host: /streaming
      broker_host: http://10.0.1.56:3000
      subfolder: /streaming
      broker_secret: "change-me"
      protocol: webstation
      emulator: pcsx2
      library_path: /romm
      label: WEBSTATION
```

`host` is the address your browser connects to. `broker_host` is the address
RomM's backend server uses to reach the broker directly, server to server,
not through your browser. If RomM and the container share a Docker network,
it can be the service name and port `3000` (`http://romm_webstation:3000`)
instead of an IP. `subfolder` should match the container's
`SUBFOLDER`. The full story, including why `host` is written as a path, is in
[Reverse proxy](/docs/deployment/reverse-proxy).

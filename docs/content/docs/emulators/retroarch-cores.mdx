---
title: "RetroArch core manifest"
description: "Which libretro core each RomM platform maps to, and whether it needs a BIOS, firmware, or key file before it will boot."
---

`retroarch_platforms.json` lists every RomM platform this repo supports and the
libretro core RetroArch uses to run it. (A libretro core is a plugin that lets
RetroArch emulate one specific system.) Most cores work as soon as you
download them. Some need a BIOS, firmware, or key file dropped into
RetroArch's system directory first, or the game just sits on a black screen
instead of booting.

This page is a summary specific to this repo, not a replacement for
libretro's own documentation. For anything not covered here, or for exact
file names and where to get them for each core, check libretro's
[core-specific BIOS documentation](https://docs.libretro.com/library/bios/#links-to-the-core-specific-bios-information),
the authoritative source this table was cross-referenced against.

Setup tiers used below:

- **Required**: the core will not boot a real game without this file in place.
- **Optional**: the core runs on a built-in HLE (High-Level Emulation)
  implementation instead of real firmware; a real file only improves accuracy
  or fixes specific titles.
- **None**: nothing to source for this platform.

A few rows are flagged because libretro's hub doesn't list this repo's exact
core name (sometimes the core is newer, or just named differently than what
the hub uses). Treat those as "check it yourself the first time you run into
that platform," not as settled fact.

## Nintendo, cartridge and handheld

| Platform | Core | Setup | Details |
| --- | --- | --- | --- |
| NES / Famicom | `mesen` | None | Cart dumps boot with nothing extra. |
| Famicom Disk System | `mesen` | Required | `disksys.rom` in the system dir. Only this platform needs it; plain NES/Famicom carts don't. |
| SNES / Super Famicom | `snes9x` | None | No BIOS concept for this core. |
| Nintendo 64 | `mupen64plus_next` | None | |
| Game Boy / Color | `gambatte` | Optional | A real boot ROM only changes splash timing; every game plays identically without one. |
| Game Boy Advance | `mgba` | Optional | `gba_bios.bin` fixes a handful of titles that rely on exact BIOS timing; HLE covers the rest. |
| Virtual Boy | `mednafen_vb` | None | |
| Nintendo DS | `melondsds` | Optional | Real firmware plus `bios7.bin`/`bios9.bin` is recommended; the core falls back to a built-in HLE BIOS. The original `melonds` core is unmaintained and crashes on launch on current buildbot builds, so don't switch back to it. |
| Nintendo DSi | `melondsds` | Required | DSi mode has no built-in fallback BIOS, so it needs `dsi_bios7.bin`, `dsi_bios9.bin`, `dsi_firmware.bin` and `dsi_nand.bin`. The core's firmware list marks them optional only because plain DS games run without them. |

## Nintendo, disc and 3D

| Platform | Core | Setup | Details |
| --- | --- | --- | --- |
| GameCube / Wii | `dolphin` | Optional | HLE boot by default; a real `IPL.bin` improves accuracy. Uses a custom save-subtree layout. |
| 3DS | `azahar` | Optional | Most dumps boot with nothing extra; encrypted `.3ds`/`.cci` files need decryption keys (`boot9.bin`/`boot11.bin`) in the system dir. This core comes from a GitHub release instead of libretro's usual build server (the buildbot), and it uses a custom save-subtree layout. This is the only way the broker supports 3DS: standalone Azahar has no IPC (a way for another program to send it commands), so there's no way for the broker to control it (see [Azahar setup](/docs/emulators/setup#azahar)). |

## Saves, states and imports

RetroArch sorts each core's files into a folder named for the core. The
folder takes the name the core reports about itself, which isn't always the
core's file name: the `dolphin` core reports `dolphin-emu` and the `azahar`
core reports `Azahar`.

- In-game saves (SRAM) go in `saves/<core name>/<game>.srm`.
- Save states go in `states/<core name>/`.

The `azahar` core is the one exception: it nests its own `Azahar/` folder
under the one RetroArch already sorted it into, landing its SD card and NAND
one level deeper, at `saves/Azahar/Azahar/`. See the 3DS bullet below.

The broker states these settings on every launch, so a setting in your own
`retroarch.cfg` can't move saves away from where every save archive already
keeps them. The platform table records each core's reported name as
`library_name`.

A [declared import](/docs/api/imports) can bring one `.srm` save into a
session only on a platform whose core loads one. The platform table records
this as `save_ram`, taken from a check of each core's source. These 24
platforms take one:

`nes`, `famicom`, `snes`, `sfam`, `n64`, `gb`, `gbc`, `gba`, `virtualboy`,
`nds`, `genesis`, `sms`, `gamegear`, `sg1000`, `sega32`, `tg16`,
`turbografx-cd`, `supergrafx`, `neo-geo-cd`, `wonderswan`, `wonderswan-color`,
`jaguar`, `colecovision` and `psx`.

On `nds`, the `.srm` is the melondsds core's NDS cart SRAM, exposed through
the standard `RETRO_MEMORY_SAVE_RAM` libretro call. The older, unmaintained
`melonds` core doesn't expose this; it manages its own `.sav` file instead.

On `psx`, the `.srm` is the SwanStation core's first memory card. The core
loads it only while its `swanstation_MemoryCards_Card1Type` option stays at
the default, `Libretro`. The broker doesn't pin this particular option, so an
imported save won't load if it has been changed in RetroArch.

The other platforms refuse a `.srm`:

- **PSP**: the PPSSPP core keeps saves as SAVEDATA folders, not a `.srm`.
  The refusal names the standalone PPSSPP module instead.
- **Wii and 3DS**: these cores keep saves in folders, not a `.srm`, and a
  `.srm` is refused as `unrecognised_layout`. Imports place folders here
  instead: Wii title folders in `saves/dolphin-emu/User/Wii/title/`, and
  Azahar's SD card and NAND folders as they already sit in
  `saves/Azahar/Azahar/` (the core nests its own `Azahar/` folder under the
  one RetroArch already sorted it into).
  [What each emulator takes](/docs/api/imports#what-each-emulator-takes)
  lists the shapes.
- **GameCube**: the core keeps saves as GCI files in its own folders, which
  imports don't place yet. The refusal is `shape_unverified`.
- **The rest**: the core keeps its save in a file of its own, or has none,
  so it would never read a `.srm`. The paths below are inside the core's
  `saves/` folder unless noted.

| Core (platforms) | Where the save is |
| --- | --- |
| `flycast` (dc) | VMU files in the system folder, `dc/vmu_save_<port>.bin`, per game. The broker pins `flycast_per_content_vmus` to `All VMUs`; its shared-by-default setting would leak saves between games |
| `fbneo` (arcade, cps1, cps2, cps3, neogeoaes, neogeomvs) | `fbneo/<driver>.fs` or `.nv`, named for the driver |
| `mednafen_ngp` (neo-geo-pocket, neo-geo-pocket-color) | `<game>.flash` |
| `handy` (lynx) | `<game>.eeprom` |
| `bluemsx` (msx, msx2) | `<game>.sram` |
| `opera` (3do) | `opera/per_game/<game>.0.srm` |
| `dosbox_pure` (dos) | `<game>.pure.zip` |
| `stella` (atari2600) | `stella/nvram/` |
| `yabasanshiro` (saturn) | `yabasanshiro/backup.bin`, shared by every game |
| `genesis_plus_gx` (segacd) | `scd_<region>.brm`, shared by every game of that region |
| `mesen` (fds) | `<game>.ips`, a patch against the disk |
| `puae` (amiga) | written to a substitute disk under `saves/`, not the mounted image. The broker pins `puae_floppy_write_redirect` to `enabled` |
| `vice_x64`, `hatari` (c64, atari-st) | written into the disk image by default; see the write-protection note below |
| `a5200`, `prosystem`, `freeintv`, `vecx`, `o2em`, `fuse` | no battery save |

The broker renames an imported save after the game being launched, whatever
it was called before. It refuses a `.sav`, `.rtc`, `.nv`, `.eep` or `.mpk`
file as needing conversion until each core's name for that file has been
checked. A save state isn't imported as a save: send it to
`PUT /api/session/state-file` after activate.

NeoCD's backup RAM has a similar problem even though `neo-geo-cd` takes a
`.srm` import: the core reads and writes its `neocd/neocd.srm` in the system
directory, shared across every game, before it applies the option that would
scope it per game. The broker symlinks that fixed path into `SAVE_DIR`
(`save_links` in the platform table), which brings it under the same
per-game archive isolation as everything else.

### VICE and Hatari floppy write protection

Unlike PUAE, neither VICE (`c64`) nor Hatari (`atari-st`) has a
write-redirect option; they can only be told to refuse writes to the mounted
disk outright (`vice_floppy_write_protection`,
`vice_easyflash_write_protection`, `hatari_floppy_write_protection`). Pinning
that on every launch would permanently block in-game floppy/cartridge saves,
so the broker only *seeds* it: the first time a game on either platform
launches with no options file on disk yet, write protection is turned on to
protect the ROM library by default. After that, whatever value is already on
disk is left alone, including a value a player changed from RetroArch's own
Quick Menu, so choosing to re-enable in-game saves (at the cost of the ROM
being writable) sticks on later launches. This is `core_option_seeds` in the
platform table, resolved against the broker's own options file by
`_resolve_core_options`, as opposed to `core_options`, which is pinned on
every launch and always wins over a same-named seed.

### DOSBox Pure mouse

DOSBox Pure's default virtual mouse only moves while RetroArch grabs the
mouse (F11). Under the stream, that grab puts the pointer under a lock that
drops the absolute mouse positions selkies sends outside Gaming Mode, so the
DOS cursor never moves. The broker seeds `dosbox_pure_mouse_input` to
`direct` on `dos`, which follows the cursor position and needs no grab. As a
seed it only applies to an options file that has never had it: an install
that already launched a DOS game keeps its saved value, and switching to
"direct" there is a Quick Menu change. A player who wants the virtual mouse
back can pick it there too.

## Choosing a core

Every platform above maps to one libretro core, the one listed in its table.
An operator can ask for a different core on that platform instead, in
RomM's `config.yml`, shorthand or block form:

```yaml
platforms:
  snes: retroarch:bsnes      # shorthand: emulator:core, split on the first ':'
  n64:                       # block form
    emulator: retroarch
    core: parallel_n64
```

`snes: retroarch` with an indented `core:` under it is invalid YAML; use one
of the two forms above.

### Tiers

`core:` accepts one of four kinds of core:

- **default**: the platform's own core from the tables above, the one this
  repo has tested the most (the "best tested" core in the table below).
- **vetted**: an alternate this repo has specifically tested on that
  platform.
- **untested**: any other core in the catalog that shares a file extension
  with the platform. It launches with every feature a vetted core has, but
  the broker can't be certain of its save layout ahead of time, so it
  launches with a warning and a checked, rather than fixed, save/state
  location. It boots only files with one of those shared extensions, or a
  `.zip` or `.7z` holding one, which RetroArch unpacks before the core
  sees it.
- **blocked**: a core this repo has confirmed is broken on that platform. It
  refuses to launch unless you opt in: `experimental_cores: true` on the
  container or on a platform block in RomM's `config.yml` (the platform
  wins), or `RETROARCH_EXPERIMENTAL_CORES=true` on the broker container.
  Either is enough, and neither is on by default.

### Finding your options

- `GET /api/retroarch/cores?platform=<slug>` lists every core offered on a
  platform, its tier, and whether it's verified; leave `platform` off to get
  every platform at once. It needs the `X-Broker-Secret` header, and a
  platform RetroArch has no core for answers `404`.
- `scripts/sync_core_info.py --tiers [--platform <slug>]` prints the same
  list from the command line, for every platform or just one.

### Saves and states when switching cores

- An in-game save (`.srm`) carries over automatically when one exists for
  the old core and the new core also takes one; RetroArch writes it into the
  new core's own save folder from then on. Switching back later carries it
  the other way.
- On an untested or blocked core the save is copied, not moved, because
  that core's save folder is a guess until it writes there. The original
  stays in the old core's folder.
- A carry never replaces a save that is as new as the incoming one. When the
  incoming save is newer, the one it replaces is kept beside it as
  `<game>.srm.bak`.
- A save state never carries over. A state left behind by another core is
  never loaded, even if one still exists on disk for it.
- The pre-switch archive isn't deleted: it stays in RomM's own save picker,
  so switching cores never loses access to what was there before.

## Report how a core works

Tried a core, or want to know how it did for someone else first? File a
report: [Report how a core works](https://github.com/romm-streaming/romm-broker/issues/new?template=core-report.yml).

A core moves from `untested` to `vetted` once it passes this repo's own
vetting test and has a few reports backing it up. A core moves to `blocked`
once a report confirms it's actually broken on that platform.
